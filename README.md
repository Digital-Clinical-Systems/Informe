## Capítulo III: Requirements Specification
### 3.1. User Stories
En esta seccion se detallan las Epics, User Stories y Technical Stories definidos para el proyecto ClinicalSync. Estos requerimientos han sido diseñados a partir de los hallazgos de las entrevistas, User Persona y el análisis del flujo de trabajo en áreas cardiovasculares.

Las User Stories reflejan las necesidades desde la óptica del profesional de la salud y del visitante de la web promocional. Por su parte, las Historias Técnicas definen los cimientos necesarios para construir el RESTful API y la seguridad del sistema.

Los criterios de aceptación se redactan en formato Gherkin, siguiendo la estructura Given – When – Then. Además, se mantienen en tiempo presente, tercera persona, sin referencia innecesaria a detalles específicos de interfaz gráfica y con condiciones comprobables.

Cuadro de Epics, User Stories y Technical Stories

| Epic / Story ID | Título | Descripción | Criterios de Aceptación | Relacionado con (Epic ID) |
| --------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------- |
| **EP-01**       | **Landing Page informativa**                    | Como visitante del sitio web, deseo conocer la propuesta de valor, planes y beneficios de ClinicalSync para evaluar su viabilidad en mi centro de salud. | **Given** que el usuario ingresa al sitio web, **When** revisa la informacion en la pagina, **Then** comprende rápidamente el enfoque en trazabilidad y comunicación cardiovascular de ClinicalSync. <br><br> **Given** que el visitante es un gerente clínico, **When** evalúa el software, **Then** localiza fácilmente la sección de características y testimonios.| —                         |
| **US-01**       | **Visualizar landing page**| Como visitante, quiero visualizar la landing page de ClinicalSync para conocer rápidamente la solución propuesta. | **Given** el visitante accede al Landing Page, **When** la página carga correctamente, **Then** visualiza información general de ClinicalSync. <br><br> **Given** que el visitante usa un navegador compatible, **When** ingresa al sitio, **Then** visualiza el contenido principal sin errores de cargar y compatibilidad.| EP-01|
| **US-02**       | **Revisar características y beneficios** | Como visitante, deseo conocer las características y beneficios del sistema para evaluar su utilidad en áreas cardiovasculares.| **Given** que el visitante está en la sección de características, **When** lee el contenido, **Then** reconoce funciones como el SBAR digital y registro de constantes. <br><br> **Given** que el visitante quiere validar el sistema, **When** lee los testimonios, **Then** encuentra opiniones positivas sobre el producto.| EP-01|
| **US-03**       | **Contactar al equipo**  | Como visitante interesado, deseo enviar mis datos a través de un formulario para solicitar información o una demostración.| **Given** que el visitante completa sus datos, **When** envía el formulario, **Then** el sistema confirma la recepción del mensaje. <br><br> **Given** que se omiten datos obligatorios, **When** se intenta enviar el formulario, **Then** el sistema alerta sobre los campos faltantes.| EP-01|
| **TS-01**       | **Despliegue Landing Page**  | Como desarrollador, deseo configurar el despliegue del sitio estático para asegurar que el Landing Page sea accesible públicamente.| **Given** que se actualiza el código fuente, **When** se aprueba en la rama principal, **Then** el sitio se despliega automáticamente. <br><br> **Given** que la página es cargada, **When** se solicitan los recursos estáticos, **Then** el servidor los entrega sin errores 404.| EP-01|
| **EP-02**       | **Gestión de Traspasos SBAR**                    | Como personal clínico, deseo estructurar la información del cambio de turno para asegurar la continuidad de la atención sin pérdida de datos. | **Given** que ocurre un cambio de turno, **When** el enfermero registra el relevo, **Then** se exige la estructura Situación, Antecedentes, Evaluación y Recomendación. <br><br> **Given** que un nuevo enfermero ingresa, **When** revisa sus pendientes, **Then** visualiza los traspasos SBAR enviados por el turno anterior.| —                         |
| **US-04**       | **Registrar traspaso SBAR**| Como enfermero cardiovascular, deseo registrar un traspaso clínico mediante el modelo SBAR para comunicar el estado del paciente.| **Given** que el enfermero inicia el registro, **When** completa el formulario SBAR y guarda, **Then** el sistema lo vincula al expediente del paciente. <br><br> **Given** que el traspaso se guarda con éxito, **When** finaliza la transacción, **Then** se muestra un mensaje de confirmación al usuario.| EP-02 |
| **US-05**       | **Consultar traspaso de turno**| Como enfermero entrante, deseo revisar el traspaso SBAR del turno anterior para continuar el cuidado sin interrupciones.| **Given** que existen traspasos previos, **When** el enfermero accede al módulo, **Then** visualiza la información clínica entregada. <br><br> **Given** que se busca un reporte específico, **When** se filtra por paciente, **Then** la lista muestra únicamente los SBAR asociados a él.| EP-02 |
| **US-06**       | **Confirmar recepción de traspaso**| Como enfermero entrante, deseo confirmar que he recibido el reporte SBAR para dejar constancia oficial de mi responsabilidad.| **Given** que el enfermero lee el SBAR, **When** hace clic en confirmar, **Then** el sistema marca el reporte como recibido. <br><br> **Given** que se consulta el estado de un traspaso nuevo, **When** nadie lo ha confirmado, **Then** se muestra con estado "Pendiente".| EP-02 |
| **TS-02**       | **Endpoints de Traspasos SBAR**  | Como desarrollador, deseo implementar los recursos REST para permitir la creación y consulta de las entregas de turno desde la aplicación.| **Given** que el cliente envía un payload SBAR válido, **When** el API lo procesa, **Then** guarda el registro y retorna estado 201. <br><br> **Given** que falta un campo obligatorio en el JSON, **When** el API lo recibe, **Then** responde con un error 400 Bad Request.| EP-01|
